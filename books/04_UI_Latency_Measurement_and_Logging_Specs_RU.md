# Стандарты и спецификации логирования задержек пользовательского интерфейса
## W3C Event Timing API, Google Core Web Vitals (INP / RAIL), WCET (MISRA C & ISO 26262)

---

## 1. Введение: Почему логирование UI должно закладываться в момент написания кода?
В профессиональной разработке программного обеспечения для интерфейсов (от встроенных панелей до мобильных ОС) существует непреложное правило:
> **«Если задержка реакции интерфейса не измеряется и не логируется в коде — она обязательно деградирует до неприемлемых значений.»**

Ниже собраны ведущие мировые стандарты, предписывающие инструментацию и мониторинг латентности пользовательского интерфейса.

---

## 2. Спецификация W3C: Event Timing API & User Timing Level 2

### Что предписывает стандарт W3C?
Консорциум W3C (World Wide Web Consortium) в спецификации *Event Timing API* стандартизировал методику разложения любого события взаимодействия человека с экраном на три фазы:

```
[ Физический тач ] 
       │ 
       ▼
 1. Input Delay (Задержка очереди событий)
       │ 
       ▼
 2. Processing Duration (Время работы обработчика события)
       │ 
       ▼
 3. Presentation Delay (Задержка рендеринга и вывода на дисплей)
       │ 
       ▼
[ Новый пиксель на экране ]
```

### Формула суммарной задержки (Interaction Latency):
$$\text{Total Latency} = \text{Input Delay} + \text{Processing Duration} + \text{Presentation Delay}$$

- **Input Delay:** время, пока событие тача лежало в очереди FreeRTOS (`xQueueReceive`), ожидая, когда процессор освободится.
- **Processing Duration:** время, за которое код выполнил функцию нажатия кнопки. **(Именно здесь в `cambrowser` была допущена ошибка — в эту фазу был включен сетевой вызов `media_radio_start()`, раздувший фазу до 2500 мс!)**
- **Presentation Delay:** время растеризации пикселей в кадровый буфер и передачи по шине MIPI-DSI (`app_lcd_flush()`).

## 3. Стандарт Google: Interaction to Next Paint (INP) & RAIL Model

Google закрепил метрику **INP (Interaction to Next Paint)** как официальный мировой стандарт измерения отзывчивости интерфейса:

### Градации качества отклика по стандарту INP:
* **$\le 200$ мс — Отлично (Good):** Пользователь ощущает плавную, мгновенную работу системы.
* **$200 - 500$ мс — Требует оптимизации (Needs Improvement):** Задержка заметна, начинает раздражать при частых действиях.
* **$> 500$ мс — Брак / Критическая деградация (Poor):** Интерфейс считается «глючным» и зависающим.

### Модель Google RAIL (Response, Animation, Idle, Load):
* **Response (Отклик):** реакция на ввод ДОЛЖНА завершиться и перерисовать экран за **меньше чем 100 мс** (в идеале 50 мс).

## 4. Встраиваемые и критические системы: MISRA C, ISO 26262 и анализ WCET

В автомобильной электронике, медицинских приборах и ответственных контроллерах действуют стандарты функциональной безопасности:
* **ISO 26262 (Functional Safety for Road Vehicles)**;
* **MISRA C Guidelines for the use of the C language in critical systems**;
* **IEC 62304 (Medical device software lifecycle processes)**.

### Требования к HMI и WCET (Worst-Case Execution Time):
1. **Детерминизм цикла обработки:** функция обработки прерываний и пользовательского ввода обязана иметь строго ограниченное максимальное время выполнения ($T_{max} \le \text{константа}$).
2. **Запрет недетерминированных операций:** категорически запрещено внутри обработчика нажатия обращаться к шинам с неопределенным временем ответа (I2C без таймаута, сокеты TCP/IP, операции со стиранием Flash-памяти).
3. **Обязательное логирование выбросов (Latency Spikes):** если время обработки превышает допустимый лимит (например, 100 мс), система обязана зафиксировать предупреждение в системный журнал с указанием дельты времени.

## 5. Практическая реализация логирования UI для ESP32-P4 в ESP-IDF

Для соблюдения этих спецификаций в нашем коде `browser.c` применяется инструментация через высокоточный таймер `esp_timer_get_time()`:

```c
// В начале обработки события тача:
int64_t t_touch_us = esp_timer_get_time();

// 1. Определение попадания и быстрая смена состояния (Optimistic UI)
s_radio_pending_idx = id - BTN_STATION;
draw_screen();
app_lcd_flush();

// 2. Замер и логирование времени отклика интерфейса:
int64_t latency_ms = (esp_timer_get_time() - t_touch_us) / 1000;
if (latency_ms > 100) {
    ESP_LOGW("UI_PERF", "⚠️ UI Лаг! Отклик экрана занял %lld мс (лимит: 100 мс)", latency_ms);
} else {
    ESP_LOGI("UI_PERF", "✅ UI Отклик: %lld мс (INP Good)", latency_ms);
}

// 3. Отправка команды сетевому плееру (не блокирует экран):
media_radio_start_async(radio_stations[s_radio_pending_idx].url);
```
